PROJECT DEFINITION
Problem statement: Laboratories and industrial facilities need a digital system to track hazardous waste through its complete lifecycle — from generation and collection through transportation, treatment/disposal, and regulatory compliance documentation — replacing unreliable paper-based tracking with centralized visibility, traceability, and accountability.

Outcome required: A centralized digital platform where every unit of hazardous waste has a unique, traceable record from creation to final disposal, with full audit history, role-based access, and compliance-support tooling.

This is a compliance-SUPPORT and tracking system, not a legal compliance guarantee. Do not invent or hardcode jurisdiction-specific legal requirements and present them as universal. Design the compliance module so regulatory rules are configurable data, not hardcoded logic. State this distinction clearly in the README and anywhere compliance status is displayed.

Frontend: React + TypeScript
Backend: Node.js + Express.js, REST API
Database: PostgreSQL
Caching/Performance: Redis
DevOps: Docker, Docker Compose, Git, GitHub
Do not replace any of these unless there is a strong, specific technical reason you cannot work around. If you introduce any additional technology, library, or service beyond this stack, you must explicitly state what it is, why the mandatory stack alone is insufficient for that need, and what the tradeoffs are.

STEP 3 — THE WASTE LIFECYCLE (CORE DOMAIN MODEL)
Implement a status-driven lifecycle, with every waste record carrying a unique, immutable tracking ID (e.g. WR-2026-000123):

draft → registered → collected → in_storage → assigned_transport
     → in_transit → delivered → in_treatment → disposed → completed
Every status transition must be written as a new row in a status_history table (never overwritten), attributed to the user who made the change, with a timestamp. A separate audit_logs table (JSONB details column) must capture broader entity-level actions (create/update/status_change) for security and compliance review — keep these two logs conceptually distinct: status_history powers the lifecycle timeline UI, audit_logs powers the security/compliance audit trail.

STEP 4 — BUILD THE ACTUAL BACKEND

JWT-based authentication (with password hashing via bcrypt or equivalent); define an access/refresh token strategy if you judge it warranted, and justify the choice
Role-based authorization middleware, enforced on every protected route
Input validation on every endpoint (e.g. zod or joi) — reject invalid input before it reaches business logic
Centralized error handling middleware with consistent error response shapes
Structured logging
Redis integration for the use cases you defined in Step 2
Pagination, filtering, sorting, and search on list endpoints (especially waste records)
Audit logging triggered from the service layer, not scattered across controllers
Strict separation of concerns: controllers stay thin (parse request → call service → shape response); all business logic lives in services; all data access lives in models/repositories
Cover, at minimum, these API resource groups: auth, users, waste records, collection, transportation, disposal/treatment, facilities, compliance, documents, dashboard/analytics, notifications, audit logs.

JWT or another justified secure auth mechanism, with sensible expiry
Role-based authorization enforced server-side on every route
Input validation and sanitization everywhere
Rate limiting (Redis-backed is acceptable and preferred)
Correct CORS configuration
Secure HTTP headers (helmet or equivalent)

Secure file upload handling (type/size validation, safe storage paths, no path traversal)

STEP 7 — DOCUMENTS, COMPLIANCE, NOTIFICATIONS, AUDIT
Documents: support manifests, transport documents, disposal certificates, and compliance documents. For the initial version, store files on a Docker-mounted volume with metadata (type, uploader, timestamp, associated waste record) in PostgreSQL. Design this so migration to S3-compatible object storage later is a config change, not a rewrite. Enforce file-type/size validation and access control on retrieval.
Compliance module: checklist-style tracking of required documents/steps per waste record, expiry tracking, missing-item detection, overdue flags — all driven by configurable rules, not hardcoded legal text. Make the "this is not a legal compliance guarantee" boundary explicit in the UI and docs.
Notifications: keep the first implementation practical — in-app notifications for events like pending collection, delayed transport, pending disposal, expiring compliance documents, overdue workflow steps. Do not over-engineer this in the MVP.
Audit trail: every significant state change must be reconstructable as "User X changed Record Y from state A to state B at time T, with these details." Protect audit data from modification through the normal application API (append-only from the application's perspective).
